// 題目 1: 需求的種類 (功能性需求)
::功能性需求::下列哪個陳述屬於典型的「功能性需求 (Functional Requirement)」？{
~系統必須在三秒內回應使用者的查詢。
~系統的平均故障間隔時間 (MTBF) 需大於 500 小時。
=系統必須允許使用者透過身分證字號和密碼進行登入。
~系統程式碼必須符合 ISO/IEC 12207 標準。
}

// 題目 2: 非功能性需求的種類 (性能)
::性能需求::「系統應支援至少 5,000 個並行使用者 (Concurrent Users) 而不降低響應時間」屬於哪一種非功能性需求？{
~安全性 (Security)。
~可用性 (Usability)。
=性能/效率 (Performance/Efficiency)。
~可移植性 (Portability)。
}

// 題目 3: 非功能性需求的種類 (安全性)
::安全性需求::下列哪一項最符合「安全性 (Security)」非功能性需求的定義？{
~系統應在所有主流瀏覽器上正常運作。
~系統的程式碼應易於修改和擴展。
=系統必須對敏感數據使用強加密演算法以防止未經授權的存取。
~系統必須達到 99.99% 的運行時間。
}

// 題目 4: 需求工程的流程
::需求工程流程::一般而言，需求工程 (Requirements Engineering) 的第一個活動是什麼？{
~需求規格撰寫 (Requirements Specification)。
~需求驗證 (Requirements Validation)。
=需求獲取/發現 (Requirements Elicitation/Discovery)。
~需求變更管理 (Requirements Change Management)。
}

// 題目 5: 需求獲取方法 (訪談 Interview)
::訪談法::在需求獲取過程中，進行「訪談 (Interview)」的主要缺點是什麼？{
=可能會因為受訪者知識不足或對未來系統有預期偏見而導致資訊不完整或失真。
~無法獲得任何定量的性能數據。
~不適合與高階經理人交流。
~耗費的時間比「民族誌 (Ethnography)」少得多。
}

// 題目 6: 需求獲取方法 (民族誌 Ethnography)
::民族誌法::「民族誌 (Ethnography)」這種需求獲取方法的特色是什麼？{
~透過虛擬的模型或圖形介面來探索使用者需求。
~專注於對系統技術架構的正式分析。
=分析人員實際觀察使用者在真實工作環境中如何執行任務。
~要求使用者填寫標準化問卷來收集統計數據。
}

// 題目 7: 需求獲取方法 (情境 Scenario)
::情境法::使用「情境 (Scenario)」或「使用者故事 (User Stories)」來描述需求的優點是？{
~可以完全取代詳細的需求規格文件。
~只能用於定義非功能性需求。
=有助於將需求放入特定的使用脈絡，使利害關係人更容易理解和確認。
~只適用於硬體控制系統的開發。
}

// 題目 8: 需求規格書撰寫的最佳實務
::規格書撰寫::撰寫需求規格書 (SRS) 時，一項重要的「最佳實務」要求是每條需求都應具備什麼特性？{
~必須用複雜的專業術語描述。
~必須包含軟體實作的程式碼片段。
=必須是清晰、可量測、完整且**可驗證 (Verifiable)** 的。
~必須始終包含解決方案的詳細資料庫結構。
}

// 題目 9: 需求驗證 (Validation)
::需求驗證::「需求驗證 (Requirements Validation)」活動的主要目標是什麼？{
~驗證最終程式碼是否符合需求規格。
~檢查需求文件中是否有錯別字和格式錯誤。
=確保系統規格文件反映了利害關係人的**真實需求**。
~將所有需求變更納入系統基線中。
}

// 題目 10: 需求變化的處理
::需求變化::在開發過程中，需求變化是不可避免的。處理需求變化的主要目的是什麼？{
~一律接受所有需求變化，以維持客戶滿意度。
~一律拒絕所有需求變化，以避免延期。
=建立一個正式流程來評估變更的影響、成本和效益，並決定是否納入。
~只在專案經理決定時才重新啟動整個需求工程流程。
}
