//  H1: 系統狀態的可見性 (Visibility of system status) 

::Nielsen_H1_Q1::根據「系統狀態的可見性」原則，系統應該在合理的時間內提供什麼？{
    =適當的回饋（Feedback）讓使用者知道目前發生了什麼事#此原則的核心在於提供即時、適當的回饋，讓使用者了解系統正在處理什麼。
    ~完整的操作日誌#操作日誌是事後紀錄，並非即時的回饋。
    ~詳細的技術錯誤代碼#技術錯誤代碼對一般使用者而言缺乏可讀性。
    ~允許使用者自由地復原動作#這是「使用者掌控與自由」的原則。
}

::Nielsen_H1_Q2::一個檔案上傳介面顯示一個動畫的進度條（Progress Bar），並標示「已完成 75%」，這是遵循了哪個啟發式原則？{
    =系統狀態的可見性#進度條和百分比明確地告知使用者上傳的狀態和進度，讓使用者保持知情。
    ~美觀與極簡設計#進度條提供了重要的狀態資訊，不能算作多餘或非必要的設計元素。
    ~辨識優於記憶#此原則關注的是操作介面，而非系統執行狀態。
    ~錯誤預防#這是一個狀態回饋，而非預防錯誤的機制。
}

::Nielsen_H1_Q3::以下哪種介面行為**最嚴重地違反**了「系統狀態的可見性」原則？{
    ~點擊按鈕後，按鈕短暫變色#按鈕變色是快速回饋，遵循了原則。
    ~系統繁忙時，操作回應略有延遲#延遲雖然影響體驗，但只要有回饋（如載入圖示）就不算嚴重違反。
    =執行複雜運算時，系統畫面凍結且無任何載入圖示#畫面凍結且無任何回饋，使使用者不知道系統是在處理中還是崩潰了，屬於嚴重的違反。
    ~儲存完成後，僅在左下角短暫顯示「儲存成功」#這是一個適當的回饋，只是可能不太明顯。
}

//  H2: 系統與真實世界的匹配 (Match between system and the real world) --------------------

::Nielsen_H2_Q4::「系統與真實世界的匹配」原則建議設計師應該如何呈現資訊？{
    =使用使用者熟悉的語言、概念和慣例#系統的語言應貼近使用者的日常生活，而非程式或技術術語。
    ~使用系統內部精確的技術術語#這是違反此原則的行為。
    ~以隨機順序呈現資訊以避免記憶負擔#資訊應以自然、合邏輯的方式呈現。
    ~採用全靜態的介面元素#此原則不涉及介面元素的動態性。
}

::Nielsen_H2_Q5::在電子郵件應用程式中使用「信封」圖示來代表收件匣，這符合了哪個啟發式原則？{
    =系統與真實世界的匹配#信封是現實世界中傳遞訊息的代表物，符合此原則。
    ~一致性與標準#雖然它也是標準，但此例更直接體現了將現實概念引入系統。
    ~使用彈性與效率#使用圖示有助於辨識，但與效率原則無直接關係。
    ~錯誤預防#與錯誤預防無關。
}

::Nielsen_H2_Q6::當一個資料庫系統使用「Tuple」和「Relation」等只有資料庫工程師才懂的術語來標註普通使用者介面上的表格和行，這違反了哪個原則？{
    ~美觀與極簡設計#雖然可能不美觀，但主要問題是使用了不熟悉的行話。
    ~辨識優於記憶#此問題是關於術語的理解，而非記憶。
    =系統與真實世界的匹配#使用了使用者不熟悉的內部技術術語，違反了應使用使用者語言的原則。
    ~幫助與說明文件#系統應在介面上即具備易懂性。
}

//  H3: 使用者掌控與自由 (User control and freedom) 

::Nielsen_H3_Q7::哪個原則強調提供明確標識的「緊急出口」（例如：復原、重做、取消）來應對使用者誤操作？{
    =使用者掌控與自由#此原則確保使用者感到能掌控系統，並能輕鬆擺脫不想要的狀態。
    ~錯誤預防#錯誤預防是在錯誤發生前阻止，而緊急出口是在錯誤發生後補救。
    ~系統狀態的可見性#這是關於回饋，而非操作控制。
    ~一致性與標準#這是關於介面元素的使用規範。
}

::Nielsen_H3_Q8::在一個多步驟的設定精靈（Wizard）中，提供一個始終可點擊的「取消（Cancel）」按鈕和一個「上一步（Back）」按鈕，主要體現了哪個原則？{
    ~一致性與標準#一致性指的是按鈕的樣式和位置，而非功能本身。
    ~錯誤預防#提供取消是補救機制，預防是事前措施。
    =使用者掌控與自由#這允許使用者隨時退出流程或返回修改，賦予使用者完全的控制權。
    ~使用彈性與效率#這不是效率加速器，而是基本的控制權。
}

::Nielsen_H3_Q9::一個網頁表單在使用者輸入大量資料後，如果使用者點擊了瀏覽器的「返回」按鈕，表單所有資料都會丟失且沒有警告，這違反了哪個原則？{
    ~錯誤預防#雖然沒有預防，但更主要的問題是使用者無法從這個丟失資料的錯誤中恢復。
    =使用者掌控與自由#使用者沒有緊急出口（如自動儲存或警告提示）來恢復或取消這個破壞性操作。
    ~系統與真實世界的匹配#這與真實世界匹配的關係不大。
    ~系統狀態的可見性#系統狀態可能可見，但重點在於缺乏控制權。
}

//  H4: 一致性與標準 (Consistency and standards) 

::Nielsen_H4_Q10::「一致性與標準」原則要求系統設計在哪些方面保持統一？{
    =介面內的相同事物應使用相同的名稱、外觀和操作方式#確保設計在內部和外部標準上都保持一致，減少使用者的學習成本。
    ~所有按鈕都必須使用相同的顏色#顏色一致性是其一部分，但原則涵蓋的範圍更廣。
    ~每年至少更新一次介面設計#與更新頻率無關。
    ~僅使用業界最流行的元件庫#應遵循標準，不一定是流行與否。
}

::Nielsen_H4_Q11::在應用程式中，所有「儲存」按鈕都使用綠色，所有「刪除」按鈕都使用紅色，這體現了哪個原則？{
    =一致性與標準#這建立了應用程式內部的操作顏色標準，方便使用者辨識和預測。
    ~美觀與極簡設計#這與設計的美感無關。
    ~系統與真實世界的匹配#這屬於介面慣例，而非真實世界的比擬。
    ~幫助與說明文件#這屬於設計規範，不需要依賴說明文件。
}

::Nielsen_H4_Q12::一個應用程式使用不同的圖示來代表多個子介面中相同的「設定」功能，這違反了哪個原則？{
    ~辨識優於記憶#雖然辨識受影響，但根本原因是缺乏標準。
    =一致性與標準#相同的概念（設定）在不同地方使用了不一致的圖示，導致使用者的認知混亂。
    ~錯誤預防#這不會直接導致操作錯誤，但會降低效率。
    ~使用彈性與效率#這會降低效率，但不是原則的主要違反點。
}

//  H5: 錯誤預防 (Error prevention) 

::Nielsen_H5_Q13::一個遵循「錯誤預防」原則的設計，其目標是什麼？{
    =在錯誤發生之前就進行防範#透過消除容易出錯的條件、提供確認或限制輸入等方式，讓錯誤根本不會發生。
    ~提供易懂的錯誤訊息#這是 H9 的範疇。
    ~允許使用者復原已發生的錯誤#這是 H3 的範疇。
    ~紀錄所有發生的錯誤#這屬於系統監控，而非使用者體驗設計原則。
}

::Nielsen_H5_Q14::在刪除一個重要文件之前，系統彈出一個確認對話框，要求使用者輸入「DELETE」來確認操作。這主要遵循了哪個原則？{
    ~使用者掌控與自由#雖然提供了取消的自由，但其主要目的是預防使用者意外刪除。
    =錯誤預防#透過額外的確認步驟，特別是要求輸入關鍵字，極大地降低了誤操作的風險。
    ~系統狀態的可見性#這不是關於狀態回饋。
    ~辨識優於記憶#與記憶負擔無關。
}

::Nielsen_H5_Q15::一個表單要求使用者輸入出生日期，但允許輸入未來的日期，這違反了哪個原則？{
    =錯誤預防#系統沒有在輸入時限制日期的合理範圍，導致使用者可能輸入無效的、自相矛盾的資料。
    ~系統與真實世界的匹配#雖然未來的生日不符合現實，但直接的設計違反是沒有限制輸入。
    ~協助使用者辨識、診斷與修復錯誤#系統尚未提供錯誤訊息，因此預防的層面更重要。
    ~一致性與標準#這不屬於標準或慣例問題。
}

//  H6: 辨識優於記憶 (Recognition rather than recall)

    ~透過複雜的指令集來加速操作#複雜指令集會增加記憶負擔。

}

    ~系統狀態的可見性#與狀態回饋無關。

    ~一致性與標準#客製化雖然可能打破一致性，但其目標是為了效率。
    ~系統與真實世界的匹配#與現實世界的比擬無關。
    ~錯誤預防#與錯誤預防無關。

//  H8: 美觀與極簡設計 (Aesthetic and minimalist design) 

::Nielsen_H8_Q22::「美觀與極簡設計」原則的核心建議是什麼？{
    =介面不應包含不相關或不常用的資訊#避免視覺干擾，確保介面內容的資訊價值最大化。

    ~介面必須包含大量高畫質圖片#圖片可能會增加視覺負擔，違背極簡精神。
