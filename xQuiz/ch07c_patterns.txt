//  Factory Method (工廠方法) --------------------

::Factory_Easy::哪個設計模式定義了一個用於建立物件的介面，但將實際例項化的工作延遲到子類別？{
    =Factory Method#工廠方法（Factory Method）讓子類別決定要實例化哪個具體類別，是物件建立的基礎模式。
    ~Abstract Factory#抽象工廠（Abstract Factory）是用於建立「一系列」相關或相互依賴物件的介面。
    ~Builder#建造者（Builder）模式用於分步驟建構一個複雜物件。
    ~Prototype#原型（Prototype）模式用於透過複製現有物件來建立新物件。
}

::Factory_Medium::在Factory Method模式中，哪個角色負責實作工廠方法以回傳具體的產品物件？{
    ~Creator (建立者)#Creator 是一個抽象類別或介面，它定義了工廠方法，但不實作它。
    =Concrete Creator (具體建立者)#具體建立者（Concrete Creator）繼承自 Creator，並實作工廠方法，以回傳其對應的具體產品實例。
    ~Product (產品)#產品（Product）是工廠方法所建立的物件的介面。
    ~Abstract Factory (抽象工廠)#抽象工廠是另一種模式，用於建立一組相關產品，而非單一產品。
}

::Factory_Hard::Factory Method 模式的主要優點是提高了系統的哪種特性？{
    =系統對新產品類別的開放性（符合開放/封閉原則）#Factory Method 允許在不修改 Creator 類別的情況下引入新的 Concrete Product 類別，符合開放/封閉原則（OCP）。
    ~執行效能的提升#設計模式主要關注架構和可維護性，通常不會顯著提升執行效能。
    ~記憶體使用量的最佳化#Factory Method 對記憶體使用的最佳化並非其主要優點。
    ~類別繼承層次的扁平化#事實上，Factory Method 會引入 Creator 和 Concrete Creator 的繼承結構。
}

//  Abstract Factory (抽象工廠) --------------------

::AbstractFactory_Easy::哪個設計模式提供一個介面，用於建立一系列相關或相互依賴的物件，而無需指定它們的具體類別？{
    =Abstract Factory#抽象工廠（Abstract Factory）模式是創建一個「產品族系」的工廠。
    ~Factory Method#工廠方法只負責創建一個單一的產品。
    ~Singleton#單例（Singleton）模式是確保一個類別只有一個實例。
    ~Builder#建造者模式關注的是複雜物件的逐步建構。
}

::AbstractFactory_Medium::Abstract Factory 模式的核心用途是什麼？{
    =確保一組產品物件在執行時保持一致性（屬於同一族系）#抽象工廠確保創建的所有產品物件都來自同一組（例如，Windows 主題的所有 UI 元件）。
    ~延遲物件的實例化過程#延遲實例化是 Factory Method 的特點之一，但非 Abstract Factory 的核心。
    ~避免子類別實作過多的工廠方法#Abstract Factory 實際上可能需要為每個產品定義一個建立方法。
    ~將物件的建立與使用解耦#這是所有創造者模式的共同點，但非 Abstract Factory 的獨特核心。
}

::AbstractFactory_Hard::相較於 Factory Method 模式，Abstract Factory 模式在擴展新**產品類型**（如新增 Checkbox 元件）時，其主要代價（缺點）是什麼？{
    =難以在不修改 Abstract Factory 介面的情況下新增產品類型#新增一個產品類型會需要修改 Abstract Factory 介面（新增一個建立方法）及其所有具體實作，違反 OCP。
    ~必須為每個具體產品族系撰寫大量重複的程式碼#程式碼重複性不是主要問題，新增介面才是關鍵。
    ~降低了系統的執行效率#設計模式主要關注架構，通常不造成顯著的執行效率問題。
    ~增加了產品之間的耦合性#產品之間依然透過抽象介面耦合，耦合性並非主要代價。
}

//  Bridge (橋接) --------------------

::Bridge_Easy::橋接（Bridge）設計模式的主要目的是什麼？{
    =將抽象部分與實作部分解耦，使它們可以獨立變化#Bridge 模式的重點在於分離抽象化（例如形狀）和實作（例如繪圖 API），使其能夠獨立擴展。
    ~確保一個類別只有一個實例#這是 Singleton 模式的目的。
    ~動態地將職責附加到物件#這是 Decorator 模式的目的。
    ~將一個類別的介面轉換成另一個客戶期望的介面#這是 Adapter 模式的目的。
}

::Bridge_Medium::在 Bridge 模式中，抽象層（Abstraction）與實作層（Implementation）之間的關係通常是如何建立的？{
    =抽象層物件持有一個實作層物件的引用（Composition/組合）#Abstraction 類別會包含一個指向 Implementation 介面的引用，透過組合實現解耦。
    ~實作層物件繼承自抽象層物件#兩者是獨立的繼承體系，不應直接繼承。
    ~抽象層物件透過靜態方法呼叫實作層#這會導致強耦合，違背 Bridge 的初衷。
    ~兩者透過全域變數進行通訊#使用全域變數是設計不良的徵兆。
}

::Bridge_Hard::使用 Bridge 模式最適合解決哪種設計問題？{
    =避免在兩個維度上（例如功能和平台）擴展時導致類別繼承爆炸#Bridge 模式將功能維度和平台維度分離，避免 $N \times M$ 個子類別的組合爆炸。
    ~處理物件的執行時狀態變化#這是 State 模式的常見用途。
    ~統一不同介面的物件以便協同工作#這是 Adapter 或 Facade 模式的用途。
    ~將複雜的子系統包裝成一個簡單的介面#這是 Facade 模式的用途。
}

//  Template Method (範本方法) --------------------

::TemplateMethod_Easy::哪個設計模式在一個操作中定義一個演算法的骨架，將一些步驟延遲到子類別中？{
    =Template Method (範本方法)#範本方法模式定義了演算法的固定流程（骨架），但將可變的步驟交給子類別實作。
    ~Strategy (策略)#策略（Strategy）模式是將整個演算法封裝在不同的類別中，並在執行時切換。
    ~Command (命令)#命令（Command）模式是將操作請求封裝為物件。
    ~Observer (觀察者)#觀察者（Observer）模式用於定義物件間一對多的依賴關係。
}

::TemplateMethod_Medium::在 Template Method 模式中，定義演算法骨架（即包含演算法步驟的方法）通常被宣告為什麼？{
    =final/sealed（最終或密封），防止子類別覆寫#範本方法本身定義了演算法的固定順序，不應被覆寫，因此通常宣告為 final/sealed。
    ~abstract（抽象），要求子類別必須實作#演算法的骨架方法是實作好的，子步驟才可能是抽象的。
    ~private（私有），只能在類別內部呼叫#如果為 private，外部將無法使用該演算法。
    ~public static（公開靜態），作為工具方法#這會使得該演算法難以使用繼承來客製化。
}

::TemplateMethod_Hard::Template Method 模式的「鉤子操作」（Hook Operation）主要用途是什麼？{
    =允許子類別選擇性地介入或修改演算法流程，但不強制實作#鉤子操作通常具有空實作或預設行為，子類別可以選擇覆寫來增加特定邏輯。
    ~強制子類別實作演算法的每個步驟#這是抽象方法（Abstract Method）的目的。
    ~用於在執行時切換演算法的實作細節#這是 Strategy 模式的目的。
    ~讓父類別可以呼叫子類別的私有方法#鉤子方法通常是 protected 或 public，而不是 private。
}

// -------------------- Composite (組合) --------------------

::Composite_Easy::哪個設計模式允許將單個物件和物件群組以一致的方式處理？{
    =Composite (組合)#組合模式的核心思想是讓客戶端對單個物件（Leaf）和物件群組（Composite）使用統一的介面。
    ~Decorator (裝飾)#裝飾模式用於動態地為物件增加職責。
    ~Adapter (轉接)#轉接模式用於轉換介面。
    ~Facade (門面)#門面模式用於提供子系統的統一介面。
}

::Composite_Medium::在 Composite 模式中，扮演「容器」角色並包含其他元件（Component）的是哪個類別？{
    =Composite (組合)#Composite 類別實作了 Component 介面，並且維護了對其子元件的引用，是容器的角色。
    ~Leaf (葉節點)#Leaf 是群組中的單個物件，不能包含其他元件。
    ~Component (元件)#Component 是抽象介面，定義了所有元件的共同操作。
    ~Client (客戶端)#客戶端是使用 Component 介面的程式碼，而非模式中的元件類別。
}

::Composite_Hard::Composite 模式在設計上的主要挑戰或權衡是什麼？{
    =必須在元件介面中包含對單個元素無意義的操作（例如 add/remove）#這是為了達成「透明性」（即客戶端無需區分 Leaf 和 Composite）而做的權衡，Leaf 實作 add/remove 通常是無意義的。
    ~客戶端需要判斷它正在處理的是 Leaf 還是 Composite 物件#理想情況下，客戶端不應該需要區分兩者（即透明性）。
    ~難以動態地改變物件的父子關係#Composite 模式通常支援動態的 add/remove 操作。
    ~容易產生循環引用#循環引用是可能的，但可以透過良好的設計來避免，並非模式本身固有的主要權衡。
}

//  Decorator (裝飾) --------------------

::Decorator_Easy::哪個設計模式允許在執行時動態地將新的行為（職責）附加到物件上？{
    =Decorator (裝飾)#裝飾模式使用組合（Composition）而非繼承來擴展物件的功能和職責。
    ~Strategy (策略)#策略模式是在執行時切換演算法。
    ~Chain of Responsibility (職責鏈)#職責鏈模式是將請求沿著一條鏈傳遞。
    ~Proxy (代理)#代理模式是提供一個物件的替代物或佔位符。
}

::Decorator_Medium::Decorator 模式中，Decorator 類別與它所裝飾的 Concrete Component 類別有什麼共同點？{
    =它們都實作或繼承了共同的 Component 介面/抽象類別#Decorator 必須與其所裝飾的物件具有相同的介面，以確保客戶端可以透明地使用。
    ~它們都是最終（final）類別，不能被繼承#Decorator 類別通常是可繼承的，以便建立具體的裝飾者。
    ~它們之間是繼承關係#Decorator 與 Component 之間是組合關係（Decorator 包含 Component），而非繼承。
    ~它們都包含對 Client 介面的引用#它們只實作或繼承 Component 介面，不需要知道 Client。
}

::Decorator_Hard::Decorator 模式的主要優點是解決了哪種問題？{
    =透過繼承來擴展功能所導致的類別爆炸問題#傳統上使用繼承來添加功能，會隨著功能的增加導致子類別的組合數量呈指數級增長。
    ~確保只有一個物件實例存在#這是 Singleton 模式的目的。
    ~將複雜的初始化邏輯封裝起來#這是 Builder 模式可能涉及的功能。
    ~允許物件在執行時改變其介面#這與 Decorator 的目的無關，Decorator 保持相同的介面。
}

//  Adapter (轉接) --------------------

::Adapter_Easy::哪個設計模式用於將一個類別的介面轉換成客戶端期望的另一個介面？{
    =Adapter (轉接)#轉接模式（Adapter）的目的是讓原本因為介面不相容而無法一起工作的類別能夠協同運作。
    ~Bridge (橋接)#橋接模式是用來分離抽象和實作。
    ~Decorator (裝飾)#裝飾模式是用來動態增加功能。
    ~Facade (門面)#門面模式是用來提供統一的高層次介面。
}

::Adapter_Medium::Adapter 模式有兩種常見的實現方式：類別轉接（Class Adapter）和物件轉接（Object Adapter）。物件轉接是如何實現的？{
    =透過組合（Composition），Adapter 類別持有 Adaptee 類別的一個實例#物件轉接（更常見）是透過 Adapter 類別**組合**（持有引用）不相容的 Adaptee 類別來實現介面轉換。
    ~透過繼承（Inheritance），Adapter 類別繼承 Adaptee 類別#這是類別轉接（Class Adapter）的實現方式，且只能在支援多重繼承的語言中使用。
    ~透過靜態方法呼叫#這會使轉接器無法處理多個 Adaptee 實例。
    ~透過抽象工廠建立#抽象工廠是創造者模式，與介面轉換無關。
}

::Adapter_Hard::當一個現有類別（Adaptee）有多個子類別，並且客戶端只希望將介面轉接到 Adaptee 的**某個特定方法**上時，建議使用哪種 Adapter 模式的實作方式？{
    =Object Adapter (物件轉接)#物件轉接（組合）允許 Adapter 只呼叫 Adaptee 類別的特定方法，對客戶端隱藏 Adaptee 的整個繼承結構和不必要的公共方法。
    ~Class Adapter (類別轉接)#類別轉接（繼承）會將 Adaptee 的所有公共方法都暴露給 Adapter，與此目的不符。
    ~Bridge Pattern (橋接模式)#橋接模式是用於解耦，與介面轉換無關。
    ~Decorator Pattern (裝飾模式)#裝飾模式是用於增加功能，與介面轉換無關。
}
